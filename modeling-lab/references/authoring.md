# Source-grounded authoring and verification

## Convert input into a bounded model

Use the collaborative method for concern progression; apply these input-specific decisions. All executable file paths in this reference are relative to the package workbench directory.

- **Description/architecture:** extract system boundary, owned parts versus external references, reusable types, configurations, relationships, and operational scenarios. Do not convert each noun into a part definition.
- **Interface table/ICD:** preserve endpoint roles, item/type, direction, units and applicability. Blank cells remain unknown. A connection is not automatically a flow. Separate structural connection, item flow, and behavior succession.
- **Requirements:** preserve original IDs/text, subject and measurable constraints where supported. Satisfaction is a design assertion; a verification case is a planned check, not a passed test.
- **Existing model:** validate before changing; inspect semantics and source anchors; preserve comments, supported unknown constructs and unrelated files. Prefer a bounded patch over regeneration.
- **Conversation:** ask only what changes a modeling decision. Start with boundary and one scenario; make a small draft, validate, show relevant views, then incorporate the next answer. If the source already answers a question, do not ask again. Missing protocol, performance, multiplicity or failure behavior must not be invented.

Keep a compact `evidence.json` with source IDs, paths/revisions, exact quotations or row/turn anchors, modeled fact IDs, model element names, and status (`source-backed`, `user-confirmed`, `assumption`, `unresolved`, `conflict`). Record interpretation separately from quotation. Freeze a separate reviewed `intake.json` source catalog, add the product schema-1 `evidence-contract.json`, and run `check_evidence.py --intake intake.json` for a single-source accepted package; it checks source/model revision, exact quotations and explicit declaration coverage. Read [checked syntax and evidence discipline](validated-syntax.md) for the schema route, coverage limits and community-tested counterexamples. Do not label a multi-file source set as evidence-qualified by this single-source gate. Material conflicts remain open until resolved; do not silently choose the last document. An assumption may support a clearly labeled scenario, not a claimed accepted architecture.

Use stable names derived from the input's IDs/vocabulary. Reuse the same definitions and usages across views. Resolve definition-versus-usage, composite-versus-reference, port conjugation, inheritance/redefinition and multiplicity explicitly. Use actual language constructs; never translate a generic graph into SysML by relabeling boxes.

For a new system, use the bundled workbench's `tools/reference-pilot/MODEL_PACKAGE.md` and `assess_package.py` rather than reusing the cooler's fixed acceptance runner. Prepare a system-specific `package.json`, expected-fact contract, source-support links and decision register. Every unresolved/conflicting/assumed claim must be triaged; a material conflict blocks acceptance even when no model element is attached. A resolved decision needs a cited modeled claim linked to checked facts. Questions outside the claimed scope need an explicit exclusion reason and remain visible. These records document authorized modeling judgments, not approval signatures. Do not invent resolutions for real inputs; the pump fixture's design-owner dialogue is explicitly fictional test data.

## Author and check incrementally

1. Create a small complete source model and its necessary imports. Quote requested names that are language keywords (for example `'decide'`) instead of silently renaming their meaning. The working `fixtures/workspaces/formal-monitor/model/monitor.sysml` is a validated example, not a mandatory system template. Read only constructs relevant to the task; use the matching bundled library or formal examples for unfamiliar syntax.
2. Write expected facts from the input before inspecting generated diagrams: ownership, typing, endpoint chains, directed payload, constraints, trace links, and known exclusions. Preserve these independently of the candidate text.
3. Run `qualify.py` with explicit JAR/library/source/output and optional `--views`. Fix actual diagnostics; never weaken a requirement to make the model pass. A new output directory keeps each receipt distinguishable.
4. Run citation/coverage checks as a separate gate; reject stale sources, invented quotes, uncited added usages and provisional claims presented as source-backed. Preserve the old receipt when changing evidence; review source/model deltas before rebinding hashes. Citation existence does not prove source entailment. Inspect engine `semantics` in `report.json`, not label strings. Validate expected facts with `check_contract.py` when available: check binding endpoints, behavior performance assignments and requirement expression structure rather than only relation existence or source-text substrings; examine exact diagnostic/source anchors for failures. Absence of syntax errors alone is insufficient.
5. Verify a meaningful edit and reload: the affected value/relationship changes, related views update, unrelated facts remain, and restore returns to baseline semantics. Check satisfaction subject bindings with the actual FeatureReferenceExpression referent: a short name can bind an implicit subject of the same name. Use an unambiguous qualified usage (for example `context.cooler`) when needed. Session IDs may change; compare named semantic facts and contextual occurrences, not random UUIDs.

For event-driven behavior, distinguish state exhibition, initial succession, transition source/target and each accept action's payload type. The contract's `transition` expectation resolves these from the engine and checks guard/effect counts; it does not simulate behavior or qualify arbitrary guards. `fixtures/authoring/pump-station/` demonstrates repeated skids, nested motor structure, four event transitions, mixed input types and a blocking policy conflict. Run `pump_regressions.py` for statically valid wrong-target/wrong-trigger/missing-exhibition/cross-wiring/value-edit controls. It is a second authored exercise, not a blind benchmark. Declared design counts and operating limits are not computed cardinalities or executed interlocks.

For model questions, query the current report and check its source revision, scope and exclusions before answering. For an existing-model edit, review the source diff and affected evidence/facts, apply a bounded patch, validate, inspect changed views, and retain a restore path. Do not round-trip through a partial serializer that drops unsupported constructs.

For a split model use the tool's source-set option only when supported, and retain a source map. Do not concatenate files ad hoc and claim original diagnostic line locations. The source-set runner accepts `--source-set sources.json` with `{"schemaVersion":1,"files":["types.sysml","model.sysml"]}`. It assembles declared SysML files and maps diagnostics back to original paths/lines; it does not claim native separate-resource or incremental-session equivalence. Say fresh-load validation.

## Produce the views the decision needs

Create `views.json` entries with `id`, `names` (qualified target names), `view` and `styles`. Available Pilot modes include `TREE`, `INTERCONNECTION`, `ACTION`, `STATE` and `DEFAULT`. Use `renderer: "engineering"` for supported part/port interconnection sheets; other modes use the reference renderer. An application preset is not a modeled SysML `view` or `viewpoint` declaration.

Typical concerns are context, decomposition, interconnection, behavior, requirements and verification. Choose useful concerns rather than forcing six views on every model. Start a local `lab.py` session to switch views, inspect source, and focus on a definition or usage. Verify the actual rendered consumer in the in-app browser.

- Preserve the same model facts and source revision across projections. Check distinct requested concerns/scopes, view/source hashes and exchange multiplicities; six output files or a set of exchange tuples is insufficient.
- Decomposition changes scope; reduction hides detail and reports exclusions; abstraction names its rule and supporting relationships. An aggregated edge is not a newly asserted direct connection.
- Repeated usages of a type require distinct occurrence context even when the port definition is shared. Never merge their connectors by terminal feature ID alone.
- Use the notation profile's supported shapes and line meanings. In the engineering part/port profile, definitions are rectangular, usages rounded, reference usages dashed, ports docked, binary connections undirected, bindings labeled `=`, and filled flow arrows only when explicit interface flow roles and payloads resolve. Do not fabricate arrows from `in`/`out` names. The Exchange summary mode is an explicitly analytical port reduction with supporting flow/connector IDs; it does not create direct semantic connections.
- Inspect endpoint attachment, label overlap, line/label ambiguity, long names, Fit/100% readability, and source navigation. Unsupported connectors and omitted features must be visible in the receipt/UI. If a view fails, repair it or report that view as unaccepted; do not hide it.
- Verify that viewpoint buttons actually switch the displayed diagram, selected-scope rendering works, text edits mark prior views stale, validation clears invalid results, and restoration recovers the baseline. A screenshot of working-looking controls does not prove interaction. For tall state layouts, inspect a horizontal `LR` preset before accepting labels that cross the frame or become unreadable at Fit.

For nontechnical communication, offer **Engineering** and **Stakeholder** presentations of the same qualified model. A stakeholder view answers an audience question, not just a zoom level. Lead with an actual graphical representation: component/connection maps, state/event paths or check-to-obligation diagrams derived from resolved model facts. Use short labels and an on-demand diagram key; put supporting prose behind click-to-inspect or expandable details. Do not substitute paragraphs in boxes for the primary diagram. Keep material conditions, missing relationships and readiness limits visible without expansion. Use color with labels or line styles, never color alone. Retain source revision, scope, supporting element/relationship IDs and visible omissions; never turn planned verification into a pass or remove an unresolved issue. Use reviewed domain terms and source-backed descriptions when available; identifier spacing alone does not establish functional purpose. Regenerate or invalidate summaries with their dependencies. Do not maintain a second explanatory model. The reference lab currently supports bounded component/connection overviews, direct transition stories and requirement/check context through `stakeholder.py`; arbitrary constraints, nested/concurrent behavior, native/shared view persistence and production integration remain unqualified. Inspect both modes and test source changes and unsupported scopes.

For user-defined perspectives and larger models, use the scope contract below. Use named occurrence context, decomposition depth, explicit include/hide and limited interface-neighbor expansion; selection changes the projection, not source semantics. The reference lab supports browser-local schema-1 recipes, analytical diagrams, interface matrices/registers, scoped satisfaction matrices, model-wide planned verification matrices and direct trace-source navigation. Reapply recipes only against the current validated source; renamed/missing selectors fail visibly instead of broadening scope. Native modeled views, shared governance and enterprise scalability remain separate gates.

Matrix rows/columns and relationship criteria must be explicit. Keep parallel interface records and transfer direction; preserve omitted/crossing counts and unlinked requirements. Blank means no extracted relationship within the selection, not verified absence. Distinguish scope-hidden links from missing model links, satisfaction assertions from verification plans, and both from execution/acceptance. Exclude verification objective reference scaffolding from the obligation inventory through resolved ownership. A connection list is not a controlled interface register: owner agreements, ICD/configuration revisions, characteristics, constraints and evidence need their own sourced records. Do not invent them or infer direct trace links from multi-step reachability.

Arcadia/UAF may supply stakeholder concerns or architecture layers when requested. Preserve explicit mappings and gaps; neither method is a syntax generator or a generic zoom level.

## Changes, implementation, V&V and assurance

For commissioning planning, keep these gates distinct: controlled promotion, configuration/artifact applicability, executable procedures, immutable execution/deviation/retest, accountable acceptance and operational qualification are separate gates. Distinguish ready to execute a specific test from commissioning acceptance and operational handover; bind each decision to scope, configuration, evidence and authority. These are open workflow acceptance gates, not achieved capabilities.

Read the bundled workbench's `tools/reference-pilot/LIFECYCLE.md` for executable scope and the boundary to external lifecycle services. Use one controlled source model for projections, while requirements, supplier artifacts, physical configurations and observations retain their own authority. A new source revision triggers derivation and impact review; it does not authorize a design change or edit historical evidence.

The reference lab now automatically invalidates/regenerates draft views after typing pauses, discards older in-flight responses and blocks invalid results. This remains temporary editing, without canonical persistence or external-file watching. Potential downstream impact requires explicit dependency witnesses across old and new revisions. The standalone package does not include the separate production lifecycle service; do not claim automatic artifact synchronization, causal analysis or production bridge qualification.

For external design artifacts, procedures, observations and assurance claims, register persistent IDs, controlled revisions, configuration and explicit dependency links. Verify supplied revisions against the actual content. An unlinked artifact means unknown impact. Preserve deleted links for review. Keep historical outcomes unchanged and separately mark applicability review after a dependency changes. Restoring model bytes does not establish that physical configuration or evidence applicability has been restored.

Generate verification planning candidates only for explicit verification cases and requirements. Require an independently sourced acceptance oracle, configuration/setup, stimuli/results, units/tolerances, instrumentation/calibration applicability, evidence capture, stop conditions and revision-bound review/authorization. Missing inputs produce blocked, non-executable drafts. Do not invent physical FAT/SAT procedures, interlocks, timing or approvals from a model. Distinguish procedure maturity, execution, result, applicability, disposition and acceptance; a waiver is not a pass, and verification is not stakeholder validation.

Use `capacity_analysis.py` only for its declared integer-default/greater-than-or-equal profile. A threshold change from 2 to 3 with a declared count of 2 must report a design shortfall while preserving the existing hardware model. It does not count installed equipment or prove satisfaction. Other analyses must declare and qualify their supported semantics.

Decision registers now require schema 2 with `resolutionChecks` linking each resolution to the issue's independently reviewed expected facts. Fact support must target the checked subject or an explicit checked referent. These are mechanical relevance checks, not source entailment or approval authentication. Reports must match evaluation context and preserve limitations in every format. Existing-report assessment remains distinct from fresh execution. Single-use report IDs and staged publication do not constitute a commissioning evidence repository.

When challenging usability, simulate distinct design, supplier, commissioning, V&V, assurance, configuration, operator and delivery concerns. Label simulated roles; retain real practitioner task trials, hold-out impact adjudication and owner authority as separate acceptance gates.

## Deliver

Provide source files, evidence/unknowns, expected-fact checks, view definitions, fresh validation receipts, and a usable interactive inspection route. State the actually tested construct/profile coverage. Source validity, intended-system fidelity, notation, execution, usability and production release are separate judgments. Do not claim broad engineering-grade competence from one example or a polished screenshot.
